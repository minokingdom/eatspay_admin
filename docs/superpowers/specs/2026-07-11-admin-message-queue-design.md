# 관리자 메시지 큐 설계

## 목표

관리자 대량 푸시 발송을 HTTP 요청 안에서 직접 처리하지 않고 PostgreSQL 영속 큐에 접수한다. 별도 워커가 작업을 처리하며, 관리자는 대기·진행·완료·실패 상태와 처리량을 확인하고 실패 작업을 재시도할 수 있다.

## 1차 범위

- 관리자 전체/조직별 푸시 공지 발송
- 앱 내 알림 저장과 FCM 푸시 발송
- 작업 진행률, 성공 수, 실패 수, 최근 오류 표시
- 실패 작업 수동 재시도
- 서버 및 워커 재시작 후 미완료 작업 복구
- 중복 실행 방지와 대상별 중복 발송 방지

결제 승인과 입금 콜백의 핵심 DB 처리는 큐에 넣지 않는다. SMS 인증과 개별 실시간 알림은 1차 범위에서 기존 동작을 유지하며, 안정화 후 같은 큐 구조로 확장한다.

## 구조

### PostgreSQL 작업 저장소

`message_jobs`는 작업 단위 상태를 저장한다. 주요 상태는 `queued`, `running`, `retry_wait`, `completed`, `failed`, `cancelled`다. 작업에는 유형, 요청자, 대상 조건, 메시지 내용, 전체 대상 수, 처리 수, 성공 수, 실패 수, 시도 횟수, 다음 실행 시각, 오류, 생성·시작·완료 시각을 저장한다.

`message_job_deliveries`는 사용자별 발송 상태를 저장한다. `(job_id, user_id, channel)` 고유 키로 동일 작업의 중복 발송을 막는다. 각 대상은 앱 내 알림 저장 여부와 FCM 결과를 기록한다.

### API

기존 `/api/admin/push/broadcast`는 대상 검증과 작업 생성까지만 수행하고 HTTP 202를 반환한다. 대상 목록은 작업 생성 시 DB에 고정하여 조직 변경이 진행 중인 발송에 영향을 주지 않게 한다.

관리자 전용 API는 작업 목록, 상세, 통계, 실패 작업 재시도를 제공한다. 모든 조회와 재시도는 시스템 관리자 권한을 요구하고 감사 로그를 남긴다.

### 워커

별도 `eatspay-message-worker.service`가 PostgreSQL에서 실행 가능한 작업을 가져온다. 작업 선점에는 트랜잭션과 `FOR UPDATE SKIP LOCKED`를 사용한다. 한 번에 제한된 대상 묶음만 처리하여 API 서버와 DB를 압박하지 않는다.

초기값은 작업 동시성 1, 대상 묶음 20명이다. 실패는 5초, 30초, 2분 간격으로 최대 3회 재시도한다. 한 대상의 실패가 전체 작업을 중단하지 않는다. 최종 실패는 DB에 보관한다.

워커가 비정상 종료되어 `running` 상태가 오래 유지되면 임대 만료 후 다시 `queued`로 복구한다. 대상별 고유 키와 완료 상태 검사로 재실행 시 중복 알림을 방지한다.

## 관리자 화면

기존 관리자 공통 UI를 사용해 `메시지 큐` 메뉴를 추가한다.

- 상단 요약: 대기, 처리 중, 오늘 완료, 실패
- 목록: 접수 시각, 유형, 제목, 대상 수, 진행률, 상태, 요청자
- 상세: 성공/실패 수, 최근 오류, 시도 횟수, 시간 정보
- 실패 상태에서만 재시도 버튼 표시
- 5초 주기 자동 갱신과 수동 새로고침

대량 발송 화면은 요청 접수 직후 작업 ID와 큐 화면 이동 버튼을 보여준다. 모달을 발송 완료까지 열어 두지 않는다.

## 오류 및 운영 안전장치

- API 입력 길이와 대상 수 검증
- 작업 생성과 대상 스냅샷을 하나의 DB 트랜잭션으로 처리
- FCM 호출 타임아웃 적용
- 재시도 가능한 네트워크 오류와 영구 실패 토큰 구분
- 최종 실패 원인 보존
- 큐 적체량, 가장 오래된 대기 시간, 처리 속도를 API로 제공
- 로그에 메시지 본문, 토큰, 개인정보를 그대로 출력하지 않음

## 용량 기준

현재 운영 서버는 2 vCPU, 메모리 약 2GB, 스왑 없음, Node API 단일 프로세스이며 PostgreSQL `max_connections`는 100이다. 큐 도입은 대량 푸시가 고객 요청을 장시간 점유하는 문제를 분리하지만 API 서버의 원래 처리량을 늘리지는 않는다.

초기 운영 목표는 다음과 같다.

- 단순 조회 중심 200개의 동시 활성 요청에서 오류율 1% 미만
- 500개의 짧은 동시접속 급증에서 서버 중단 없이 지연 처리
- 대량 푸시 중 일반 API p95 응답시간이 평시 대비 2배를 넘지 않음
- 워커 재시작 뒤 60초 이내 미완료 작업 재개
- 동일 작업·사용자·채널의 중복 발송 0건

이 수치는 보장치가 아니라 부하 테스트의 합격 기준이다. 운영 반영 전 `autocannon`으로 읽기 API, 로그인 사용자 API, 큐 발송 동시 상황을 각각 측정해 실제 허용 동시접속과 요청 처리량을 확정한다.

## 테스트

- 저장소 단위 테스트: 작업 생성, 선점, 진행률, 재시도, 임대 만료 복구
- 중복 방지 테스트: 동일 delivery 재처리 시 한 번만 저장·발송
- API 테스트: 202 접수, 권한, 목록, 상세, 재시도
- 워커 테스트: 일부 대상 실패 후 나머지 계속 처리
- 관리자 UI 테스트: 상태 렌더링, 자동 갱신, 실패 작업 재시도
- 운영 검증: syntax, 전체 테스트, UI guardrail, systemd 상태, health check
- 부하 테스트: 평시, 200 활성 요청, 500 burst, 푸시 워커 동시 실행 비교

## 배포와 롤백

DB 스키마를 먼저 추가하고 API를 배포한 뒤 워커 서비스를 시작한다. 관리자 UI는 마지막에 반영한다. 큐 기능 플래그를 두어 문제가 발생하면 기존 대량 발송 버튼을 일시 중지할 수 있게 한다. 롤백 시 큐 테이블은 삭제하지 않고 워커만 정지하여 작업과 오류 기록을 보존한다.
